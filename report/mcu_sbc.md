# MCU와 SBC 역할 나누기

> 엣지 장비에서 SBC(싱글 보드 컴퓨터)와 MCU(마이크로컨트롤러)가 각각 무엇을 맡을지, MCU를 붙인다면 어디에 어떻게 붙일지 정리한 문서.

## 0. 결론

- **영상 처리는 SBC(Jetson Orin Nano)가 전부 맡는다.** 지금 계획 그대로다. (`report/hardware.md`, `report/container.md`)
- **MCU는 영상을 다루지 않고, "SBC가 멈췄을 때 되살리는 역할"만 맡는다.** 하드웨어 워치독(멈추면 리셋·전원 재투입)과 정전 시 안전 종료 신호가 주 용도다.
- MCU는 **필수가 아니다.** 처음에는 Jetson 내장 워치독 + Docker `restart`로 시작하고, 현장 시험에서 "원격으로 못 살리는 멈춤"이 생기면 MCU를 붙인다. 부품값은 약 1만 원 안쪽이다.
- 후보 MCU는 **RP2040(Raspberry Pi Pico)** 이다. 무선이 없어 보안상 노출이 적고, 3.3V 신호가 Jetson 40핀 헤더와 맞는다.
- 아직 부품을 사거나 연결해 보지 않았다. 핀 번호·전류 수치는 데이터시트로 다시 확인한다. (6장)

## 1. MCU와 SBC 차이

| 항목 | MCU (예: RP2040, ESP32, STM32) | SBC (예: Jetson Orin Nano, 라즈베리파이 5, RK3588) |
|---|---|---|
| 운영체제 | 없음 또는 RTOS. 전원 켜면 바로 내 코드가 돈다 | Linux. 부팅에 수십 초 |
| 연산 성능 | 수백 MHz, RAM 수백 KB | GHz급 멀티코어, RAM 수 GB, GPU·NPU |
| 전력 | 수십 mW ~ 0.5W | 5 ~ 25W |
| 신뢰성 | 구조가 단순해 멈출 일이 거의 없음 | 커널·드라이버·메모리 부족 등으로 멈출 수 있음 |
| 잘하는 일 | 핀 제어, 타이머, 센서 읽기, 정해진 시간 안에 반응 | 영상 디코딩, 딥러닝 추론, 네트워크, Docker |
| 영상 처리 | 저해상도 흑백 이미지에 아주 작은 모델 정도 (ESP32-S3 등) | RTSP 다채널 디코딩, YOLO 추론 |

- 예시 그림(로봇)에서 "절대 죽으면 안 되는" 모터·비상정지는 보통 MCU에 둔다. Linux가 멈춰도 MCU는 계속 돌기 때문이다.
- 이 프로젝트에는 모터가 없으므로, MCU에 맡길 "절대 죽으면 안 되는 일"은 **SBC를 감시하고 되살리는 일**이 된다.

## 2. 이 시스템에서 역할 나누기

```
            AC 220V
               │
          [소형 UPS] ──(정전 신호: USB 또는 접점)──┐
               │ DC 19V                           │
               ├────────────────┐                 │
               │                ▼                 ▼
               │        ┌──────────────┐   ┌──────────────────────────┐
               │        │ 상시 닫힘 릴레이 │◀──│ MCU (RP2040)              │
               │        └──────┬───────┘   │  - 하트비트 감시           │
               │               │ 19V       │  - 리셋 핀 / 전원 재투입    │
               │               ▼           │  - 정전 → 종료 요청        │
               │     ┌──────────────────┐  │  - (선택) 케이스 온도       │
               │     │ SBC: Jetson      │  └──────────┬───────────────┘
               │     │  vision/broker/  │◀─ UART ─────┘  하트비트·명령
               │     │  uplink/watchdog │◀─ 리셋 핀 ──────  (3.3V)
               │     └──────────────────┘
               ▼
       MCU 전원 (5V 강압, 릴레이 앞단에서 받음)
```

| 할 일 | 맡는 곳 | 이유 |
|---|---|---|
| 영상 디코딩·전처리·YOLO·추적·카운팅 | **SBC** | GPU·NVDEC가 필요. MCU로는 불가 |
| 1분 집계 전송, 전송 큐, 날씨 명령 | **SBC** | 네트워크·TLS·디스크 큐 필요 |
| 컨테이너 하나가 죽었을 때 재시작 | **SBC** (Docker `restart`) | 박스 전체를 껐다 켤 필요 없음 |
| Linux 커널이 멈췄을 때 리셋 | **SBC 내장 워치독** → 안 되면 **MCU** | 내장 워치독이 1차, MCU는 내장 워치독도 못 살리는 경우 대비 |
| 리셋으로도 안 살아날 때 전원 재투입 | **MCU** | SBC가 자기 전원을 끊었다 켤 수는 없음 |
| 정전 시 안전 종료 | UPS가 USB면 **SBC(NUT)**, 접점 신호면 **MCU** | SSD 파일 시스템 손상 방지 |
| 케이스 온도·팬 | 기본은 **SBC** (Jetson 자체 팬 제어), 케이스 팬을 따로 둘 때만 MCU | 역사 안 여름철 밀폐 케이스 대비 |

### 2.1 MCU로 영상을 처리하지 않는 이유

- 카메라마다 MCU(예: ESP32-S3 + 카메라)를 붙여 현장에서 바로 세는 방식도 생각할 수 있다. 하지만
  - MCU용 모델은 96×96 흑백 수준이라, 출구에서 여러 명이 겹쳐 걷는 장면의 검출·추적이 안 된다.
  - 방향별 통과를 세려면 추적(ByteTrack)이 필요한데, MCU 메모리로는 어렵다.
  - 결국 카메라마다 전원·네트워크를 끌어와야 해서 PoE IP 카메라보다 나을 게 없다.
- 그래서 **영상은 IP 카메라 → SBC**, MCU는 SBC 보조로만 쓴다.

## 3. 하드웨어 워치독 동작

### 3.1 단계별 복구

먼저 가벼운 방법을 쓰고, 안 될 때만 다음 단계로 간다.

| 단계 | 상황 | 누가 | 조치 |
|---|---|---|---|
| 1 | vision 컨테이너 하나가 죽음 (메모리 부족 등) | Docker | `restart: on-failure`로 그 컨테이너만 재시작 |
| 2 | Docker·broker·uplink 전체가 응답 없음 | watchdog 컨테이너 → 호스트 | 하트비트를 멈춤 → MCU가 감지 |
| 3 | Linux 커널 멈춤 | Jetson 내장 워치독 | SoC 리셋 |
| 4 | 하트비트가 3분 넘게 없음 | MCU | Jetson 리셋 핀을 잠깐 당김 |
| 5 | 리셋 뒤 5분 안에 하트비트가 안 돌아옴 | MCU | 릴레이로 19V를 10초 끊었다 다시 연결 |
| 6 | 5단계를 3번 해도 실패 | MCU | 더 이상 반복하지 않고 대기 (현장 점검 대상). 상태 LED로 표시 |

- 6단계에서 멈추는 이유: 고장 난 SSD 등으로 영영 안 켜지는 경우, 전원을 계속 끊었다 켜면 부품이 더 상한다.
- 리셋·전원 재투입 횟수는 다음 부팅 때 MCU가 UART로 SBC에 알려주고, SBC는 이 숫자를 상태 정보(`health`)에 넣어 클라우드로 보낸다. 원격에서 "이 역은 어젯밤 전원 재투입 1회"를 볼 수 있다.

### 3.2 하트비트는 "앱이 살아 있음"을 뜻해야 한다

- 단순히 Linux가 살아 있다고 하트비트를 보내면, Docker가 멈춘 상황을 못 잡는다.
- 그래서 하트비트는 `report/container.md`의 **④ watchdog 컨테이너**가 보낸다. broker에 붙어 있고 uplink가 응답할 때만 보낸다.
- 반대로 **카메라 하나가 멈춘 것으로는 하트비트를 끊지 않는다.** 카메라 하나 때문에 박스 전체를 재시작하면 나머지 9대의 카운트까지 빠진다. 카메라 문제는 Docker 재시작과 클라우드 알림으로 처리한다.

### 3.3 MCU와 SBC 연결

| 신호 | 방식 | 비고 |
|---|---|---|
| 하트비트·명령 | UART (Jetson 40핀 헤더 UART ↔ RP2040 UART), 3.3V | USB로 연결해도 됨 (RP2040 USB 시리얼). UART가 USB보다 드라이버 문제가 적음 |
| 리셋 | MCU GPIO → Jetson 개발키트 버튼 헤더의 리셋 핀 | 오픈 드레인(또는 트랜지스터)으로 GND에 잠깐 붙임. 핀 위치는 개발키트 문서로 확인 |
| 전원 재투입 | MCU GPIO → 릴레이 모듈 → Jetson 19V 입력 | **상시 닫힘(NC)** 릴레이를 써서, MCU가 고장 나거나 꺼져도 Jetson 전원은 유지 |
| 정전 신호 | UPS 접점 → MCU GPIO | UPS가 USB 신호면 MCU 없이 SBC에서 NUT로 처리 |

- **MCU 전원은 릴레이 앞단에서 받는다.** Jetson 전원을 끊을 때 MCU까지 같이 꺼지면 다시 켤 수 없다.
- 컨테이너에서 UART를 쓰려면 watchdog 컨테이너에만 그 UART 장치(`/dev/ttyTHS*`)를 `devices:`로 넘긴다. privileged는 쓰지 않는다.
- Jetson 개발키트가 전원이 들어오면 자동으로 켜지는지(자동 전원 켜기 설정) 확인한다. 꺼진 채로 대기하면 5단계 전원 재투입이 소용없다.

## 4. 부품 후보

| 부품 | 대략 가격 | 전압·전력 | 통신 | 비고 |
|---|---|---|---|---|
| **Raspberry Pi Pico (RP2040)** | 약 $4 | 5V 입력(1.8~5.5V), 약 0.1W | UART, GPIO, USB | **1순위.** 무선 없음, 자체 워치독 내장, 3.3V 신호 |
| ESP32-C3 개발보드 | 약 $5 | 5V 입력, 약 0.3~0.5W (무선 끄면 낮음) | UART, GPIO, Wi-Fi, BLE | 무선이 필요 없는데 붙어 있어 보안 점검 대상이 늘어남 |
| STM32 (예: Nucleo, Blue Pill) | 약 $5~15 | 3.3~5V | UART, GPIO | 산업용으로 많이 쓰임. 개발 환경이 Pico보다 번거로움 |
| 릴레이 모듈 (1채널, NC 접점) | 약 $2~3 | 코일 5V, 접점 DC 30V 3A 이상 | GPIO | Jetson 19V × 최대 약 1.3A보다 여유 있게 |
| 5V 강압 모듈 | 약 $2 | 입력 19V → 출력 5V | — | MCU·릴레이 코일 전원 |

- MCU 쪽 부품을 모두 더해도 **약 $10 내외**이고, 소비 전력은 1W 미만이라 `report/hardware.md` 4장 전력 합계에 거의 영향이 없다.

## 5. 개인정보·보안

- MCU는 영상·인원 수를 다루지 않고, 외부 네트워크에도 연결하지 않는다. 오가는 것은 하트비트와 리셋·재투입 횟수뿐이다.
- 무선이 없는 MCU(RP2040)를 고르면, 역사 안에서 무선으로 MCU에 접속해 박스 전원을 끄는 공격 경로가 생기지 않는다.
- MCU 펌웨어에는 키·비밀번호를 넣지 않는다. 넣을 일도 없다.

## 6. 확인이 필요한 항목

- [ ] Jetson 내장 워치독만으로 현장 시험 기간 동안 원격 복구가 되는지 (MCU 필요 여부 판단)
- [ ] Jetson Orin Nano 개발키트 버튼 헤더의 리셋 핀 위치와 전압 (개발키트 문서)
- [ ] 개발키트 자동 전원 켜기 설정 방법
- [ ] Jetson 40핀 헤더 UART 장치 이름과 JetPack에서 기본으로 켜져 있는지
- [ ] UPS 정전 신호 방식 (USB HID인지 접점인지) → MCU에 연결할지 결정 (`report/hardware.md` 2장 소형 UPS)
- [ ] 워치독 시간 값(하트비트 3분, 리셋 뒤 대기 5분)을 vision 재시작·TensorRT 엔진 로드 시간 실측으로 조정
- [ ] MCU를 쓰기로 하면 `report/hardware.md` 부품 목록과 전력 합계에 추가
