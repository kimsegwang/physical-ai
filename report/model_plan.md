# 모델 선정 · 학습 · 검증 계획

> 지하철 개찰구 혼잡도 예측 시스템의 모델 선정 근거, 학습 계획, 검증 방법을 정리한 문서.

## 0. 현재 상태

- **학습은 아직 하지 않았다.** COCO로 사전학습된 YOLO(`models/yolov8n.pt`)를 그대로 사용 중이다.
- **검증은 로직 검증까지만 완료됐다.** `tests/test_pipeline.py`의 테스트 33개는 가짜 검출기와 단위 테스트로 파이프라인 동작을 확인한 것이며, 실제 지하철 환경에서의 정확도를 확인한 것은 아니다. (구성은 3장 검증표 참고)
- 실제 YOLO 실행은 ultralytics 예제 이미지(bus.jpg) 1장으로 동작만 확인했다.
  - 검출 단계만 잰 시간: 개발 PC CPU 기준 프레임당 약 66ms (파이프라인 전체 시간이 아님)
  - 같은 이미지를 아래로 밀어 만든 25프레임으로 카운팅까지 이어지는 것을 확인 (퇴장 3명)
- **카메라 시점은 아직 정해지지 않았다.** 이 문서의 탑뷰(천장 시점) 이야기는 가정이며, 현장 조사(체크리스트 1-1 설치 높이, 1-2 촬영 각도) 결과에 따라 바뀐다.

## 1. 모델 선정

이 제품에는 두 종류의 모델이 필요하다.

| 구분 | 위치 | 역할 | 선정 모델 |
|---|---|---|---|
| 비전 모델 | 엣지 (Jetson) | 개찰구 통과 인원 카운팅 | YOLO 경량 모델 + ByteTrack 방식 추적 + 이중 통과선 |
| 예측 모델 | 클라우드 | 10분·30분 후 혼잡도 예측 | LightGBM |

### 1.1 비전 모델: 검출 + 추적 방식

영상으로 인원을 세는 방식은 크게 두 가지다.

| 방식 | 대표 모델 | 장점 | 단점 |
|---|---|---|---|
| 검출 + 추적 | YOLO + ByteTrack | 한 명씩 구분, 이동 방향 판별 가능 | 극심한 밀집에서 겹침 발생 |
| 밀도 맵 | CSRNet 등 | 수천 명 밀집 상황에 강함 | 이동 방향을 알 수 없음 |

**선정: 검출 + 추적 방식**
- 개찰구는 입장·퇴장 방향을 구분해야 하고, 통과선을 넘었는지 판정하려면 사람을 개별로 따라가야 한다.
- 개찰구 구조상 승객이 한 줄씩 통과하므로 개별 검출이 가능하다.

### 1.2 모델 크기와 비교 후보

엣지 장비 한 대가 카메라 10대 × 10fps, 즉 **초당 100프레임**을 처리해야 하므로 nano급 경량 모델로 시작한다.

| 후보 | 비고 |
|---|---|
| `yolov8n` | 현재 사용 중 |
| `yolo11n` | 설치된 ultralytics 8.4.174에 포함 |
| `yolo26n` | 설치된 ultralytics 8.4.174에 포함 (도움말 기본 예시 모델) |

- 세 모델을 **우리 현장 영상의 카운팅 정확도**와 **Jetson 실측 처리 속도**로 비교해 고른다.
- nano급으로 정확도가 부족하면 small(s)급과 비교한다.

### 1.3 검출 대상: 사람 전체 vs 머리 (현장 조사 후 결정)

COCO 사전학습 모델은 주로 옆·정면에서 찍은 사람으로 학습됐다. 카메라가 천장에서 수직으로 내려다보면 머리와 어깨만 보여 성능이 떨어질 수 있다. 다만 **우리 영상으로 측정한 적은 아직 없으며**, 비스듬한 각도라면 사전학습 모델로도 충분할 수 있다.

| 검출 대상 | 장점 | 단점 |
|---|---|---|
| 사람 전체 | 박스가 커서 추적이 안정적, COCO의 캐리어 등 다른 클래스를 함께 쓸 수 있음 | 밀집 시 몸이 서로 겹침 |
| 머리 | 사람끼리 붙어 있어도 머리는 잘 겹치지 않음 | 아래 세 가지 |

**머리 검출의 단점**
1. **작은 박스로 인한 추적 끊김**
   - 머리 약 20cm, 보행 1.3m/s, 10fps라고 가정하면 한 프레임에 13cm를 움직인다. 이때 앞뒤 프레임 박스의 IoU는 약 0.21로, 현재 매칭 기준(`match_iou_min` 0.2)에 걸린다. 1.5m/s면 약 0.14로 기준 아래가 된다. 몸 전체 박스는 같은 조건에서 약 0.4다. (모두 가정값으로 계산한 추정치)
   - 새 트랙은 속도를 모르는 상태이고 한 번만 놓쳐도 지워지므로, 확정되지 못해 **누락**으로 이어진다.
2. **우산·모자·후드 가림**: 탑뷰에서는 우산이 머리를 완전히 가린다. 비 오는 날(가이드 5.2), 체크리스트 6-3 "우산 소지·모자·후드"와 직결된다.
3. **보조 클래스 상실**: 머리만 학습하면 COCO의 캐리어(28번) 같은 클래스가 사라져, 캐리어를 카운트에서 빼는 확인 기능을 쓸 수 없다. 필요하면 머리와 캐리어·유모차를 함께 라벨링해야 한다.

**머리 검출로 정하면 코드에서 바꿔야 할 것**
- 추적: 머리 크기의 빠른 박스로 추적 테스트를 추가하고, 끊기면 처리 fps를 올리거나 매칭 방식(중심점 거리 등)을 보강
- `counting.anchor`: `bottom`(발 위치) 대신 `center`. 비스듬한 시점이면 통과선을 바닥이 아니라 머리가 지나가는 높이 기준으로 다시 긋기
- `detection.aux_classes`: COCO 번호(28)를 새 모델 클래스에 맞게 바꾸거나 비우기
- `detection.person_class`: 새 모델의 클래스 번호와 이름이 맞는지 확인
- 박스 크기 기준(`ref_person_area_*`)과 신뢰도 기준(0.4)을 새 모델로 다시 측정

**결정 기준**: 현장 영상으로 사람 전체 모델의 카운팅 정확도를 먼저 재고, 밀집 시 겹침으로 인한 누락이 주원인일 때만 머리 검출을 검토한다.

### 1.4 예측 모델: LightGBM

- 입력: 최근 인원 수, 시간대, 요일, 공휴일, 날씨, 행사 정보 등 표 형태 데이터
- 표 형태 데이터에서는 딥러닝보다 트리 기반 모델이 적은 데이터로도 성능이 좋고 빠르다.
- 학습 전에 정할 것: 예측 대상(개찰구 분당 인원인지, 혼잡 등급인지), 필요한 데이터 기간, 집계에서 `clipped_*`(한계 초과로 잘라냄)·`spike_*`(급증) 표시가 붙은 분을 학습에서 다루는 방법

## 2. 학습 계획

### 2.1 공개 데이터셋

| 데이터셋 | 내용 | 시점 | 이용 조건 |
|---|---|---|---|
| SCUT-HEAD | 머리 박스 (PartA 교실 감시카메라 2,000장, PartB 웹 이미지 2,405장) | 비스듬한 감시카메라 시점, 탑뷰 아님 | 원문: "학술 연구 목적에 한해 무료" |
| CrowdHuman | 머리 박스 + 보이는 몸 박스 + 전체 몸 박스 | 공식 페이지에서 확인 불가 | 비상업 연구·교육 목적 한정, 이미지 재배포 금지 (제3자 미러에서 확인, 공식 출처 재확인 필요) |

**공개 데이터셋 사용 규칙**
- **비상업 연구·교육 용도로만 사용하고, 상용화(FlowSight 제품)에는 쓰지 않는다.**
- **이미지를 재배포하지 않는다.** 저장소에 올리지 않고 `data/`(Git 제외)에만 둔다.
- SCUT-HEAD는 "학술 연구"만 명시돼 있어, 수업 과제가 포함되는지는 사용 전에 확인한다.
- 탑뷰 시점 데이터가 아니므로, 탑뷰로 결정되면 현장 영상이 반드시 필요하다.

### 2.2 현장 영상 수집과 동의

- 실제 역 촬영은 운영 기관 허가가 필요하다.
- 초기에는 동의를 받은 인원이 강의실 출입문을 통과하는 장면을 위에서 촬영한다.
- 현장 조사 체크리스트의 조건(피크·한산, 역광, 비 오는 날·우산, 캐리어 등)이 고르게 포함되도록 수집한다.
- **촬영 동의서에 반드시 적을 것**
  - 영상을 **Google Colab(외부 클라우드)에 업로드해 학습에 쓴다**는 사실. 제품은 영상을 외부로 보내지 않지만, 학습 단계의 업로드는 외부 전송이다.
  - 보관 위치(`data/`, Git 제외), 보관 기간, 학습 후 삭제 시점

### 2.3 라벨링

- 영상에서 1~2초 간격으로 프레임을 추출한다. (연속 프레임은 거의 같은 장면이라 의미가 적다)
- Roboflow, CVAT 등의 도구로 사람(또는 머리)에 박스를 표시한다. 캐리어 확인이 필요하면 캐리어·유모차도 함께 표시한다.
- 초기 목표: 1,000~3,000장

### 2.4 학습 데이터 전처리 일치

- 실제 운영에서 모델에 들어가는 영상은 **리사이즈 → ROI 크롭 → 마스크 → (깜빡임 보정) → (CLAHE)**를 거친 영상이다. (`src/subway_edge/preprocess.py`)
- 학습 이미지도 **같은 현장 설정(configs/*.json)으로 같은 전처리를 거쳐야** 학습과 운영의 입력이 일치한다. 원본 프레임으로 학습하면 크기·밝기·가려진 영역이 달라 성능이 떨어질 수 있다.
- 프레임을 파일로 저장하는 일은 CLAUDE.md의 "영상·프레임을 파일로 저장하는 코드를 만들지 않는다" 규칙에 걸린다. 따라서
  - 제품 코드(`src/subway_edge/`)에는 넣지 않고, **동의받은 학습 데이터 전용 도구로 분리**한다.
  - 결과는 `data/`에만 저장하며, 이 도구는 사용자 승인 후 작성한다.

### 2.5 데이터 분할

- 같은 영상의 프레임을 무작위로 학습·검증용으로 나누면, 거의 같은 장면이 양쪽에 들어가 점수가 실제보다 높게 나온다.
- **촬영 날짜 또는 장소 단위로 분할한다.** 예: 월~목 영상은 학습, 금요일 영상은 테스트
- 날짜로만 나누면 같은 장소·같은 카메라라서 **다른 역에서도 통하는지**는 알 수 없다. 장소가 2곳 이상이면 한 곳을 통째로 테스트용으로 남긴다.
- 예측 모델은 **시간 순서로** 나눈다. (과거로 학습, 이후 기간으로 테스트. 무작위로 섞지 않는다)

### 2.6 학습

- 처음부터 학습하지 않고, COCO 사전학습 모델에서 이어서 학습(파인튜닝)한다.
- 개발 PC는 CUDA를 사용할 수 없어 CPU 학습이 매우 느리므로, **Google Colab 무료 GPU로 학습**하고 결과 모델 파일만 받아온다. (업로드는 2.2의 동의 범위 안에서만)

**파일 위치 규칙**

| 파일 | 위치 | Git |
|---|---|---|
| 학습 설정 yaml (데이터 경로·클래스 이름) | `configs/train/` (예: `configs/train/gate.yaml`) | 올림 (학습을 재현할 수 있게) |
| 학습 이미지·라벨 | `data/` | 올리지 않음 |
| 사전학습·학습 완료 모델 | `models/` | 올리지 않음 |
| 학습 결과물 (`runs/`: 가중치, 학습 이미지 샘플 `train_batch*.jpg` 등) | `runs/` | 올리지 않음 (`.gitignore`에 포함, 샘플 이미지에 사람이 찍힘) |

```bash
yolo train model=models/yolov8n.pt data=configs/train/gate.yaml epochs=100 imgsz=640
```

- `model=yolov8n.pt`처럼 경로 없이 쓰면 현재 폴더에 모델을 내려받으므로, 항상 `models/` 경로를 붙인다.
- 1.2의 비교 후보(`yolo11n`, `yolo26n`)도 같은 데이터·같은 설정으로 학습해 비교한다.

### 2.7 배포용 변환 (TensorRT)

- **Jetson에서 직접 변환한다.** TensorRT 엔진은 GPU와 TensorRT 버전에 종속되므로, Colab이나 개발 PC에서 만든 엔진은 Jetson에서 쓸 수 없다.
- **FP16을 먼저 시도한다.** 정확도 손실이 거의 없고 보정 데이터가 필요 없다. 처리 속도가 부족할 때만 INT8로 간다.
- **INT8은 현장 이미지로 보정(calibration)한다.** 보정 데이터를 지정하지 않으면 ultralytics는 coco128(일반 시점 사진)로 보정하므로, 반드시 우리 데이터 yaml을 지정한다.
- 설치된 ultralytics 8.4.174에서는 `int8`·`half` 대신 `quantize` 옵션을 쓴다.

```bash
yolo export model=models/best.pt format=engine quantize=16                                 # FP16
yolo export model=models/best.pt format=engine quantize=8 data=configs/train/gate.yaml     # INT8 (현장 이미지로 보정)
```

- 변환 후에는 **카운팅 정확도를 다시 검증**한다.

## 3. 검증 방법

| 단계 | 확인 내용 | 기준 | 현재 상태 |
|---|---|---|---|
| 로직 검증 | 파이프라인 동작 | 시나리오·단위 테스트 통과 | ✅ 33개 통과 (아래 구성), 예제 이미지 1장 실행 확인 |
| 검출 성능 | 모델이 사람(또는 머리)을 잘 찾는지 | 테스트셋 mAP50, 정밀도·재현율 | ❌ 학습 전 |
| 카운팅 정확도 | 실제 인원과 숫자가 맞는지 | 수동 카운트 대비 95% 이상 (PRD KPI) | ❌ 실제 영상 필요 |
| 시스템 성능 | 엣지 장비 실시간 처리 | Jetson 한 대에서 카메라 10대 × 10fps = 초당 100프레임, 24시간 안정 동작 | ❌ Jetson 필요 |
| 예측 정확도 | 10분 후 혼잡도 예측 | WAPE 15% 이하 + "현재 값 유지"보다 낮을 것 (PRD KPI), MAE 함께 보고 | ❌ 누적 데이터 필요 |

**로직 검증 테스트 33개 구성**

| 구분 | 개수 | 내용 |
|---|---|---|
| 전체 경로 (가짜 검출기) | 11 | 입장·퇴장, 되돌아감, 선 근처 흔들림, 꼬리물기 2종, 짧은 오검출, ROI 좌표, 마스크, 검출 필터, 젖은 바닥 마스크 |
| 집계 | 4 | 물리 한계 잘라내기, 급증 플래그, 급증 아님 판정, 빈 분 처리 |
| 설정·자동 전환 | 11 | 혼잡도 전환, 날씨·외투, 프로필이 현장값보다 약해지지 않음, 잘못된 설정 거부, 설정 파일 |
| 전처리 | 5 | 샘플링, 리사이즈, 흔들림 보정, 깜빡임 보정, CLAHE 자동 전환 |
| 전송 | 2 | 1분 집계 전송, JSON 출력 |

### 3.1 가장 중요한 지표: 카운팅 정확도

- 검출 점수(mAP)가 높아도 추적이 끊기면 숫자가 틀린다.
- 최종 판단은 **"실제 통과 인원 대비 몇 명으로 셌는가"**로 한다.
- 측정 방법은 `report/preprocess.md` 4장을 따른다.
  - 시간대·입장/퇴장별로 따로 측정
  - 오검출과 누락을 분리해서 기록
  - 전처리를 하나씩 추가하며 정확도 변화 기록
- 정답 데이터 후보: 운영 기관에서 개찰구 통과 기록(교통카드 태그)을 받을 수 있다면 수동 카운트보다 큰 규모로 검증할 수 있다. 꼬리물기는 기록에 없다는 점을 감안한다. (확보 가능 여부 확인 필요)

### 3.2 예측 지표: MAPE 대신 WAPE·MAE

- MAPE는 분마다 `|오차| ÷ 실제값`을 평균하므로, 실제 인원이 **0명인 분에서는 계산이 불가능**하고 0에 가까우면 값이 폭발한다. 한산한 시간·야간에는 0명인 분이 많다.
- **WAPE = 전체 |오차| 합 ÷ 전체 실제 인원 합.** 0명인 분이 있어도 계산되고, 사람이 많은(실제로 중요한) 시간대의 오차가 크게 반영된다.
- **MAE(평균 절대 오차, 명 단위)**를 함께 보고해, 한산한 시간대의 오차를 사람 수로 직관적으로 확인한다.

### 3.3 비교 기준

| 모델 | 비교 대상 |
|---|---|
| 비전 모델 | 사전학습 `yolov8n` / `yolo11n` / `yolo26n` vs 파인튜닝 후 모델 (같은 테스트 영상, 카운팅 정확도·Jetson 처리 속도) |
| 예측 모델 | ① 현재 값 유지 (직전 값을 그대로 예측값으로) ② 지난주 같은 시간 값 ③ LightGBM |

- 10분 뒤처럼 짧은 예측에서는 ① "현재 값 유지"가 매우 강한 기준이다. LightGBM이 이 기준보다 낫지 않으면 쓸 이유가 없다.
