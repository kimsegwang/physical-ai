# PRD: 지하철 개찰구 혼잡도 예측 시스템

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.0 |
| 작성일 | 2026-10-06 |
| 배치 방식 | 엣지(인원 카운팅) + 클라우드(혼잡도 예측) 혼합 구조 |

> 본 문서의 규모·비용 수치는 비교 분석을 위한 가정값이다.
> (역 300곳, 역당 개찰구 카메라 10대, 하루 20시간 운행)

---

## 1. 문제 정의

### 1.1 현재 상황
- 출퇴근 시간대 일부 역은 승강장 밀집도가 높아 안전사고 위험이 크다.
- 승객은 역에 도착하기 전까지 혼잡 여부를 알 수 없어, 혼잡을 피할 선택(출발 시간 조정, 다른 역·노선 이용)을 하지 못한다.
- 역무원은 CCTV를 눈으로 보고 혼잡을 판단하기 때문에 대응이 늦고, 사람마다 판단 기준이 다르다.

### 1.2 해결하려는 문제
1. **실시간성 부족:** 현재 혼잡도를 승객과 역무원이 즉시 알 수 없다.
2. **예측 부재:** 앞으로 10~30분 뒤 혼잡해질지 미리 알 수 없어 사전 대응이 불가능하다.
3. **프라이버시 우려:** 하루 수백만 명의 얼굴이 찍히는 영상을 외부로 전송·저장하는 방식은 개인정보 위험이 크다.
4. **비용 문제:** 모든 카메라 영상을 클라우드에서 분석하면 연 약 96.8억 원(분석 78.8억 + 회선 18억)이 든다.

### 1.3 해결 방향
- **엣지:** 역마다 AI 박스를 두고 개찰구 영상에서 통과 인원 수만 센다. 영상은 역 밖으로 나가지 않는다.
- **클라우드:** 전체 역의 인원 수 데이터를 모아 혼잡도를 예측하고, 앱·전광판에 제공한다.

## 2. 사용자 시나리오

### 시나리오 1. 출근하는 직장인 (승객)
> 김민수(32)는 매일 8시에 강남역에서 출근한다.

1. 집을 나서기 전 지하철 앱에서 강남역 혼잡도를 확인한다.
2. 앱에 "현재 혼잡, 20분 뒤 보통으로 완화 예상"이 표시된다.
3. 10분 늦게 출발하거나 한 정거장 떨어진 역을 이용하기로 결정한다.
4. **결과:** 혼잡을 피해 덜 붐비는 시간에 탑승한다.

### 시나리오 2. 역무원 (현장 운영자)
> 박지영(41)은 잠실역 역무원이다.

1. 야구 경기가 끝난 직후, 역무실 단말에 "15분 뒤 매우 혼잡 예상" 알림이 뜬다.
2. 혼잡이 시작되기 전에 안전요원을 승강장에 배치하고 일부 개찰구를 출구 전용으로 전환한다.
3. **결과:** 혼잡이 몰리기 전에 대응해 안전사고 위험을 줄인다.

### 시나리오 3. 관제센터 운영자
> 관제센터는 전체 300개 역을 한 화면에서 모니터링한다.

1. 대시보드에서 노선별·역별 혼잡도 지도를 확인한다.
2. 특정 구간이 혼잡해질 것으로 예측되면 임시 열차 투입을 검토한다.
3. **결과:** 데이터 기반으로 열차 배차를 조정한다.

### 시나리오 4. 인터넷 장애 상황
1. 한 역의 인터넷 회선이 끊긴다.
2. 엣지 AI 박스는 계속 인원을 세고, 역사 내 전광판에는 실시간 혼잡도가 계속 표시된다.
3. 회선이 복구되면 그동안 쌓인 인원 수 데이터가 클라우드로 전송된다.
4. **결과:** 장애 중에도 현장 안내는 유지되고 데이터 손실이 없다.

## 4. 기술 스택

### 4.1 엣지 (역사 내 AI 박스)
| 구분 | 기술 | 선택 이유 |
|---|---|---|
| 하드웨어 | NVIDIA Jetson Orin Nano | 저전력으로 카메라 10대 동시 처리 가능 |
| 사람 검출 모델 | YOLO 경량 모델 (nano급, 약 30MB) | 작고 빠르며 사람 검출 성능이 검증됨 |
| 추적·카운팅 | ByteTrack + 가상 통과선(line crossing) | 같은 사람을 중복으로 세지 않음 |
| 추론 최적화 | TensorRT (INT8 양자화) | 엣지 장비에서 추론 속도 향상 |
| 로컬 저장 | SQLite | 인터넷 장애 시 인원 수 데이터 임시 보관 |
| 데이터 전송 | MQTT | 가볍고 끊김에 강한 IoT 통신 방식 |
| 배포 | Docker 컨테이너 + OTA 업데이트 | 300개 역에 원격으로 모델 일괄 배포 |

### 4.2 클라우드 (중앙 서버)
| 구분 | 기술 | 선택 이유 |
|---|---|---|
| 데이터 수신 | AWS IoT Core | 다수 엣지 장비의 MQTT 메시지 수신·관리 |
| 시계열 저장 | TimescaleDB | 시간대별 인원 데이터 저장·조회에 적합 |
| 혼잡도 예측 | LightGBM (기본) / LSTM (고도화) | 시간대·요일·날씨·행사 등 외부 변수 반영 |
| API 서버 | FastAPI | 앱·전광판에 혼잡도 데이터 제공 |
| 관제 대시보드 | Grafana | 전체 역 혼잡도 실시간 시각화 |
| 모델 재학습 | 주 1회 배치 학습 | 계절·노선 변화 반영 |

### 4.3 데이터 흐름
```
[개찰구 카메라] → [엣지 AI 박스]
                   사람 검출 → 추적 → 통과 인원 카운트
                   (영상은 처리 직후 폐기)
                        │
                        ├─→ [역사 전광판] 실시간 혼잡도 (인터넷 불필요)
                        │
                        ▼ MQTT (인원 수 숫자만 전송)
                   [클라우드]
                   데이터 저장 → 혼잡도 예측 → API
                        │
                        ├─→ [승객 앱] 현재·예측 혼잡도
                        ├─→ [역무원 단말] 혼잡 예상 알림
                        └─→ [관제 대시보드] 전체 역 현황
```

## 5. 범위 / 비범위

### 5.1 범위 (In Scope)
- 개찰구 카메라 기반 입장·퇴장 인원 카운팅
- 역별 실시간 혼잡도 4단계 표시 (여유 / 보통 / 혼잡 / 매우 혼잡)
- 10분·30분 후 혼잡도 예측
- 역사 내 전광판 표시 (인터넷 장애 시에도 동작)
- 승객 앱용 혼잡도 조회 API
- 역무원 단말 혼잡 예상 알림
- 관제센터 대시보드
- 엣지 장비 원격 모델 업데이트

### 5.2 비범위 (Out of Scope)
- **얼굴 인식 및 개인 식별:** 사람 수만 세며, 누구인지는 식별하지 않는다.
- **원본 영상 저장·전송:** 영상은 엣지에서 처리 후 즉시 폐기한다.
- **열차 칸별 혼잡도:** 차량 내부 센서가 필요하므로 이번 범위에서 제외한다. (2단계 검토)
- **승강장 내부 카메라 분석:** 1단계는 개찰구만 대상으로 한다.
- **교통카드 결제 데이터 연동:** 기관 간 협의가 필요해 제외한다.
- **범죄·이상행동 감지:** 별도 프로젝트로 분리한다.
- **자동 열차 배차 조정:** 예측 정보만 제공하며, 배차 결정은 관제센터가 한다.
