# PRD: 지하철 출구별 혼잡도 예측 시스템

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.1 |
| 작성일 | 2026-10-06 (v1.1 수정: 2026-10-14) |
| 배치 방식 | 엣지(인원 카운팅) + 클라우드(혼잡도 예측) 혼합 구조 |
| 카메라 위치 | 출구 계단·에스컬레이터 입구, 환승 통로 (개찰구 통과 인원은 교통카드 데이터 몫) |

> **v1.1 변경 요약:** 카메라를 개찰구에서 출구·환승 통로로 옮겼다. 개찰구 통과 인원은 교통카드 태그로 이미 정확히 집계되므로, 카메라는 교통카드가 보지 못하는 곳(어느 출구로 오가는지, 환승 동선)을 맡는다. 근거는 1.3 참고.

## 1. 문제 정의

### 1.1 현재 상황
- 출퇴근 시간대 일부 역은 출구 계단과 대합실 밀집도가 높아 안전사고 위험이 크다.
- 승객은 역에 도착하기 전까지 혼잡 여부를 알 수 없어, 혼잡을 피할 선택(출발 시간 조정, 다른 출구·역·노선 이용)을 하지 못한다.
- 출구가 여러 개인 역에서도 특정 출구 하나에 사람이 몰리는 경우가 많지만, 승객은 어느 출구가 붐비는지 알 방법이 없다.
- 역무원은 CCTV를 눈으로 보고 혼잡을 판단하기 때문에 대응이 늦고, 사람마다 판단 기준이 다르다.

### 1.2 해결하려는 문제
1. **실시간성 부족:** 현재 혼잡도를 승객과 역무원이 즉시 알 수 없다.
2. **예측 부재:** 앞으로 10~30분 뒤 혼잡해질지 미리 알 수 없어 사전 대응이 불가능하다.
3. **출구 단위 정보 부재:** 기존 데이터는 역 단위까지만 있어 "몇 번 출구가 붐비는지"를 알 수 없다.
4. **프라이버시 우려:** 하루 수백만 명의 얼굴이 찍히는 영상을 외부로 전송·저장하는 방식은 개인정보 위험이 크다.
5. **비용 문제:** 모든 카메라 영상을 클라우드에서 분석하면 연 약 96.8억 원(분석 78.8억 + 회선 18억)이 든다.

### 1.3 교통카드 데이터와의 관계

개찰구를 지나는 인원은 교통카드 태그 기록으로 이미 정확히 집계된다. 같은 일을 카메라로 다시 하지 않고, 교통카드가 보지 못하는 부분을 카메라가 맡는다.

| 알고 싶은 것 | 교통카드 태그 기록 | 출구·통로 카메라 |
|---|---|---|
| 역 전체 입장·퇴장 인원 | **정확함** | 출구 합계로 추정 가능 |
| 몇 번 출구로 들어오고 나가는지 | 모름 (역 단위까지만 기록) | **앎** |
| 같은 역 안에서 환승하는 인원 | 대부분 모름 (환승객은 개찰구를 지나지 않음) | 환승 통로에 두면 **앎** |
| 실시간 데이터 접근 | 운영 기관 내부에만 있음. 공개 통계는 시간대별 집계이고 공개까지 시차가 있음 | 우리가 직접 가짐 |

- **카메라의 몫:** 출구별·통로별 방향 통과 인원
- **교통카드의 몫:** 역 전체 입장·퇴장 인원. 공개 통계(역별·시간대별 승하차 인원)는 예측 모델의 입력과 카메라 카운팅 검증에 쓴다. 실시간 연동은 기관 협의가 되면 추가한다.
- 그래서 개찰구에는 카메라를 두지 않는다.

### 1.4 해결 방향
- **엣지:** 역마다 AI 박스를 두고 출구 계단·환승 통로 영상에서 방향별 통과 인원 수만 센다. 영상은 역 밖으로 나가지 않는다.
- **클라우드:** 전체 역의 출구별 인원 수와 교통카드 공개 통계를 모아 혼잡도를 예측하고, 앱·전광판에 출구 단위로 제공한다.

## 2. 사용자 시나리오

### 시나리오 1. 출근하는 직장인 (승객)
> 김민수(32)는 매일 8시에 강남역에서 내려 회사로 간다.

1. 집을 나서기 전 지하철 앱에서 강남역 혼잡도를 확인한다.
2. 앱에 "11번 출구 매우 혼잡, 10번 출구 보통. 20분 뒤 완화 예상"이 표시된다.
3. 10분 늦게 출발하거나, 내린 뒤 10번 출구로 나가기로 결정한다.
4. **결과:** 붐비는 출구 계단을 피해 덜 붐비는 동선으로 이동한다.

### 시나리오 2. 역무원 (현장 운영자)
> 박지영(41)은 잠실역 역무원이다.

1. 야구 경기가 끝난 직후, 역무실 단말에 "15분 뒤 7번 출구 유입 매우 혼잡 예상" 알림이 뜬다.
2. 혼잡이 시작되기 전에 7번 출구 계단에 안전요원을 배치하고, 역사 안내 방송으로 인접 출구 이용을 유도한다. 대합실이 붐비면 일부 개찰구를 출구 전용으로 전환한다.
3. **결과:** 특정 출구에 몰리기 전에 대응해 안전사고 위험을 줄인다.

### 시나리오 3. 관제센터 운영자
> 관제센터는 전체 300개 역을 한 화면에서 모니터링한다.

1. 대시보드에서 노선별·역별 혼잡도 지도와 혼잡한 출구 목록을 확인한다.
2. 환승 통로 인원이 급증하는 역이 보이면, 해당 구간의 임시 열차 투입을 검토한다.
3. **결과:** 데이터 기반으로 열차 배차와 현장 인력을 조정한다.

### 시나리오 4. 인터넷 장애 상황
1. 한 역의 인터넷 회선이 끊긴다.
2. 엣지 AI 박스는 계속 인원을 세고, 역사 내 전광판에는 출구별 실시간 혼잡도가 계속 표시된다.
3. 회선이 복구되면 그동안 쌓인 인원 수 데이터가 클라우드로 전송된다.
4. **결과:** 장애 중에도 현장 안내는 유지되고 데이터 손실이 없다.

## 3. 성공 지표 (KPI)

### 3.1 기술 지표
| 지표 | 목표 |
|---|---|
| 인원 카운팅 정확도 | 95% 이상 (수동 집계 대비) |
| 실시간 혼잡도 갱신 주기 | 5초 이내 |
| 10분 후 혼잡도 예측 오차 (WAPE) | 15% 이하, "현재 값 유지" 예측보다 낮을 것 (잠정, 데이터 누적 후 재설정) |
| 엣지 장비 가동률 | 99.5% 이상 |
| 인터넷 장애 시 데이터 유실률 | 0% (복구 후 전송) |
| 원본 영상 외부 전송 건수 | 0건 |

> 예측 오차는 MAPE 대신 WAPE(전체 |오차| 합 ÷ 전체 실제 인원 합)로 잰다. 한산한 시간·야간에는 인원이 0명인 분이 많아 MAPE는 계산이 불가능하거나 값이 폭발하기 때문이다. 자세한 근거는 `report/model_plan.md` 3.2 참고.

> 교통카드 통계를 확보하면 정확도를 역 단위로 한 번 더 확인한다. 모든 출구에 카메라가 있는 역에서는 "출구 입장 인원 합계 ≈ 개찰구 입장 태그 수"가 되어야 한다. 비상계단·연결 통로처럼 카메라가 없는 동선이 있으면 차이가 나므로 기준으로 쓰기 전에 역 구조를 확인한다.

### 3.2 서비스 지표
| 지표 | 목표 |
|---|---|
| 앱 혼잡도 조회 수 | 출시 6개월 내 일 10만 회 |
| 혼잡 시간대 승객 분산 효과 | 피크 15분 최대 인원 10% 감소 |

## 4. 기술 스택

### 4.1 엣지 (역사 내 AI 박스)
| 구분 | 기술 | 선택 이유 |
|---|---|---|
| 하드웨어 | NVIDIA Jetson Orin Nano | 저전력으로 카메라 10대 동시 처리 가능 |
| 사람 검출 모델 | YOLO 경량 모델 (nano급, 약 30MB) | 작고 빠르며 사람 검출 성능이 검증됨 |
| 추적·카운팅 | ByteTrack + 가상 통과선(line crossing) | 같은 사람을 중복으로 세지 않음 |
| 추론 최적화 | TensorRT (INT8 양자화) | 엣지 장비에서 추론 속도 향상 |
| 로컬 저장 | SQLite | 인터넷 장애 시 인원 수 데이터 임시 보관 |
| 데이터 전송 | MQTT | 가볍고 끊김에 강한 IoT 통신 방식 |
| 배포 | Docker 컨테이너 + OTA 업데이트 | 300개 역에 원격으로 모델 일괄 배포 |

### 4.2 클라우드 (중앙 서버)
| 구분 | 기술 | 선택 이유 |
|---|---|---|
| 데이터 수신 | AWS IoT Core | 다수 엣지 장비의 MQTT 메시지 수신·관리 |
| 시계열 저장 | TimescaleDB | 시간대별 인원 데이터 저장·조회에 적합 |
| 혼잡도 예측 | LightGBM (기본) / LSTM (고도화) | 시간대·요일·날씨·행사·교통카드 통계 등 외부 변수 반영 |
| API 서버 | FastAPI | 앱·전광판에 혼잡도 데이터 제공 |
| 관제 대시보드 | Grafana | 전체 역 혼잡도 실시간 시각화 |
| 모델 재학습 | 주 1회 배치 학습 | 계절·노선 변화 반영 |

### 4.3 데이터 흐름
```
[출구·환승 통로 카메라] → [엣지 AI 박스]
                          사람 검출 → 추적 → 출구별 방향 통과 인원 카운트
                          (영상은 처리 직후 폐기)
                               │
                               ├─→ [역사 전광판] 출구별 실시간 혼잡도 (인터넷 불필요)
                               │
                               ▼ MQTT (인원 수 숫자만 전송)
[교통카드 공개 통계] ───→ [클라우드]
 (역별·시간대별 승하차)    데이터 저장 → 혼잡도 예측 → API
                               │
                               ├─→ [승객 앱] 출구별 현재·예측 혼잡도, 우회 출구 안내
                               ├─→ [역무원 단말] 혼잡 예상 알림 (출구 지정)
                               └─→ [관제 대시보드] 전체 역 현황
```

## 5. 범위 / 비범위

### 5.1 범위 (In Scope)
- 출구 계단·에스컬레이터 입구, 환승 통로 카메라 기반 방향별 통과 인원 카운팅
- 출구별·역별 실시간 혼잡도 4단계 표시 (여유 / 보통 / 혼잡 / 매우 혼잡)
- 10분·30분 후 혼잡도 예측
- 혼잡 출구의 인접 출구 우회 안내
- 역사 내 전광판 표시 (인터넷 장애 시에도 동작)
- 승객 앱용 혼잡도 조회 API
- 역무원 단말 혼잡 예상 알림
- 관제센터 대시보드
- 엣지 장비 원격 모델 업데이트
- 교통카드 공개 통계를 예측 입력과 카운팅 검증에 활용

### 5.2 비범위 (Out of Scope)
- **얼굴 인식 및 개인 식별:** 사람 수만 세며, 누구인지는 식별하지 않는다.
- **원본 영상 저장·전송:** 영상은 엣지에서 처리 후 즉시 폐기한다.
- **개찰구 통과 인원 카메라 카운팅:** 교통카드 태그로 정확히 집계되므로 카메라로 다시 세지 않는다.
- **개찰구 앞 대기열 밀집도:** 통과선 대신 구역 안 인원을 세는 방식이 필요해 2단계에서 검토한다.
- **열차 칸별 혼잡도:** 차량 내부 센서가 필요하므로 이번 범위에서 제외한다. (2단계 검토)
- **승강장 내부 카메라 분석:** 1단계는 출구와 환승 통로만 대상으로 한다.
- **교통카드 실시간 데이터 연동:** 기관 간 협의가 필요해 1단계 필수 조건에서 제외한다. 공개 통계는 사용한다.
- **범죄·이상행동 감지:** 별도 프로젝트로 분리한다.
- **자동 열차 배차 조정:** 예측 정보만 제공하며, 배차 결정은 관제센터가 한다.

## 6. ROI 한 줄

**초기 투자 9억 원(AI 박스 300대)으로 전량 클라우드 분석 대비 연 약 95억 원을 절감해 2개월 안에 투자를 회수하고, 승객 얼굴 영상의 외부 전송을 0건으로 만든다.**

> 계산 근거: 클라우드 전량 분석 연 96.8억 원 − (엣지 운영 0.5억 + 클라우드 예측 서버 약 1억) ≈ 연 95.3억 원 절감

> 출구는 서로 떨어져 있어 개찰구보다 배선이 길어진다. PoE 랜선은 100m가 한계라 스위치 추가나 광케이블이 필요할 수 있고, 지상 출구는 방수 카메라가 필요하다. 이 설치비는 위 9억 원에 포함되지 않았으며 현장 조사 후 추가한다.
